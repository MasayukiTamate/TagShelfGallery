# GazoTools 設計プロトコル / Linux + Tkinter 実装ルール

## 1. 目的

この文書は、理想のアプリを構築するための設計プロトコルと、Linux 上での Tkinter 実装ルールを定義する。

対象は、ローカル画像管理・整理・閲覧・AI補助を行うデスクトップアプリであり、以下を重視する。

- シンプルな構成
- Linux での動作安定性
- GUI とロジックの分離
- 依存の失敗に対する優雅なフォールバック
- 画像管理アプリとしての扱いやすさ

---

## 2. Linux での Tkinter の評価

### 2.1 まとめ

Linux での Tkinter は「実用的」だが、次の条件を満たす必要がある。

- Python に tkinter が入っている
- X11/Wayland でディスプレイが利用可能である
- ファイルドラッグ&ドロップやマルチウィンドウが必要なら `tkinterdnd2` を使う
- GUI を使わない CI / headless 環境では import だけで済ませる設計が必要

### 2.2 長所

- Python 標準の GUI ライブラリなので導入が簡単
- Windows / Linux / macOS で大きく差が小さい
- 小さなローカルアプリ向き
- 画像ビュー、ファイル一覧、設定ダイアログの組み合わせが簡単

### 2.3 注意点

- Linux では DISPLAY / Wayland の設定が必要
- サーバー用途や CI では GUI 表示ができない
- ドラッグ&ドロップは追加パッケージが必要
- 高度な UI は Tkinter の制約にぶつかることがある

### 2.4 実務上の判断

Tkinter は以下の用途には適している。

- 画像整理アプリ
- ローカルファイル管理アプリ
- 小規模デスクトップツール
- 個人向けツール

逆に、以下には向かない。

- 複雑な Web UI を再現したいアプリ
- 高度な 3D / リッチ UI
- マルチプラットフォームの大きなアプリ基盤

## 3. 設計原則

### 3.1 GUI とロジックの分離

原則として、以下を分離する。

- GUI 層: Tkinter のウィンドウ表示、イベント処理
- ロジック層: ファイル検索、設定保存、画像処理、AI 判定
- 状態層: AppState が全体の現在状態を持つ
- データ層: JSON / CSV / ファイル入出力

禁止事項:

- GUI から直接巨大なロジックを呼ばない
- グローバル変数を過剰に増やさない
- アプリ状態を複数箇所に分散させない

### 3.2 状態は AppState に集約する

状態の管理ルール:

- current_folder
- current_files
- current_folders
- move_dest_list
- show_folder_window
- show_file_window
- ss_mode
- settings
- window_geometries
- vector_display

上記はすべて AppState を通す。

ルール:

- UI 要素は AppState を参照する
- 更新は callback で通知する
- 直接的な変数共有を避ける

### 3.3 依存は「必須」「任意」「オプション」で分ける

設計ルール:

- 必須依存: tkinter, PIL, json, os
- 任意依存: tkinterdnd2
- オプション依存: torch, torchvision, transformers

AI 系の依存は必須化しない。

理由:

- Python 環境に必ず入るとは限らない
- モデルが使えないときでもアプリを開ける必要がある
- 依存がない環境でも「通常の視聴・整理」機能は維持できる

### 3.4 起動プロトコル

アプリ起動時の推奨順序は次の通り。

1. ロガー初期化
2. AppState 初期化
3. 必須依存のチェック
4. 設定ファイルの読み込み
5. ImageCache の初期化
6. UI の作成
7. 初期フォルダの読み込み
8. 主要ウィンドウの表示

起動時に失敗しても、以下を守る。

- 例外を握りつぶさない
- ログに詳細を残す
- 失敗した機能だけを無効化する
- アプリ全体を止めない

## 4. GUI 実装ルール

### 4.1 UI はスレッドセーフにする

Tkinter はメインスレッドで UI 更新を行うのが基本である。

決まり:

- GUI 更新は UI スレッドで行う
- バックグラウンド処理はスレッドで行う
- `after()` や callback で UI へ戻す

禁止事項:

- 非 UI スレッドから Tkinter 要素を直接更新しない
- 長時間処理を UI スレッドで動かさない

### 4.2 ウィンドウ生成は基本的に最小限にする

設計ルール:

- メインウィンドウを一本とし、必要な補助ウィンドウのみ追加する
- 評価ウィンドウ、情報ウィンドウ、ベクトルウィンドウは独立で管理する
- 画面状態は AppState に保存する

### 4.3 画像表示は軽量化を優先する

- 画像はリサイズして描画する
- 既に読み込んだ画像はキャッシュする
- タイル表示やサムネイルは先読みで高速化する
- 過大な画像をそのまま描画しない

### 4.4 ドラッグ&ドロップは optional とする

Linux ではドラッグ&ドロップを使うなら `tkinterdnd2` が必要。

ルール:

- 基本機能は通常のファイル選択に依存する
- drag & drop は機能拡張として扱う
- パッケージが無い場合でもファイル選択で動作する

---

## 5. バックグラウンド処理プロトコル

### 5.1 処理の分離

重い処理は以下のどちらかで分離する。

- スレッド
- 非同期ジョブキュー
- 長時間処理の別プロセス

### 5.2 進捗の通知方法

進捗通知は次の形式を守る。

- `start` で開始
- `progress` で進行
- `finish` で完了
- `error` で失敗

禁止事項:

- 処理中に UI を直接固定させない
- 進捗がなく長時間固まるような状態を許容しない

### 5.3 AI 処理の設計ルール

AI モデルは強制依存にしない。

- model available = false の場合でもユーザーはファイル閲覧できる
- AI 機能だけが無効化される
- 常に「通常の整理・閲覧」機能が動く

---

## 6. 設定管理ルール

### 6.1 設定は JSON で保存する

保存対象:

- last_folder
- geometries
- settings
- move_dest_list
- show_* などの UI 設定

ルール:

- 1ファイルにまとめて保存する
- 未定義キーは defaults から補完する
- 保存に失敗してもアプリが落ちない

### 6.2 デフォルト値は必ず定義する

設定ファイルにキーがない場合でも、アプリが安全に動くようにする。

例:

- `show_file`
- `show_folder`
- `ss_interval`
- `ss_ai_threshold`
- `move_dest_count`

---

## 7. エラー処理ルール

### 7.1 失敗時の優先順位

1. ログを残す
2. ユーザーにわかりやすいメッセージを出す
3. 機能を無効化する
4. アプリ全体を落とさない

### 7.2 例外の分類

- ConfigError: 設定の異常
- FileHashError: ハッシュ計算失敗
- ImageLoadError: 画像読み込み失敗
- AIModelError: モデル利用不能
- VectorProcessingError: ベクトル処理失敗
- UIError: GUI 層の異常

---

## 8. 実装ポリシー

### 8.1 最低限の実用性

理想のアプリは、次の状態を満たすべき。

- Linux で起動できる
- 画像フォルダを開ける
- 一覧とプレビューが動く
- 画像を開いて見られる
- 設定が保存される
- AI は使えなくても基本機能は維持される

### 8.2 拡張の優先順位

1. 基本機能の安定
2. ファイル管理の快適さ
3. AI 補助機能
4. 高度な可視化と自動整理

---

## 9. このプロジェクトに対する適用ルール

今の GazoTools では以下を守る。

- `AppState` を中心に状態管理する
- `GazoToolsLogic` はロジック層として扱う
- AI 系は optional にする
- `tkinterdnd2` は選択依存とし、未導入でも動くようにする
- import 失敗時は例外をログで記録し、機能を無効化する
- Linux での GUI 環境が無い場合は headless モードと明確に分離する

---

## 10. 結論

Linux 上の Tkinter は、ローカル画像管理アプリには十分に現実的な選択肢である。

重要なのは「Tkinter を使う」のではなく、「Tkinter を安全に使う設計」を持つことだ。

- 依存を明確に分離する
- GUI とロジックを切る
- AI を optional にする
- 例外を受け止めて無効化する
- Linux / headless / GUI 環境差を吸収する

これが理想のアプリに向けた設計ルールの基本である。
